---

La localisation de SiteForge repose sur deux systèmes complémentaires :

1. **`LocalizedString`** — pour les textes fournis par la configuration JSON (titres, sous-titres, libellés de section…). Résolution par locale via `LocalizationContext`.
2. **i18next / react-i18next** — pour les chaînes internes aux composants et modules (formulaires, boutons, messages d'erreur…). Enregistrement statique par namespace via `addResourceBundle`.

Le hook **`useT`** unifie les deux mécanismes derrière une seule API.

---

## `LocalizedString` dans la configuration

```ts
// src/types/locale-schema.ts
import { z } from "zod";

export const LOCALES = ["fr", "en", "es", "de"] as const; // extensible
export type Locale = (typeof LOCALES)[number];

export function createLocalizedStringSchema(defaultLang: Locale) {
  // 1) Génère un objet { fr: z.string().min(1).optional(), en: …, es: …, de: … }
  const shape = LOCALES.reduce((acc, locale) => {
    acc[locale] = z.string().min(1).optional();
    return acc;
  }, {} as Record<Locale, z.ZodOptional<z.ZodString>>);

  // 2) En fait un objet Zod partiel, puis raffine pour exiger la langue par défaut
  return z
    .object(shape)
    .partial()
    .refine(obj => Boolean(obj[defaultLang]), {
      message: `Le libellé doit inclure la langue par défaut (${defaultLang})`,
      path: [defaultLang],
    });
}

export const LocalizedString = createLocalizedStringSchema("fr");
export type LocalizedString = z.infer<typeof LocalizedString>;
```

- `createLocalizedStringSchema(defaultLang)` génère un schéma Zod où chaque locale est optionnelle, sauf la langue par défaut qui est requise via `refine()`.
- Toute valeur textuelle fournie par le site utilise ce format :

  ```json
  { "headline": { "fr": "Bienvenue", "en": "Welcome" } }
  ```

## Initialisation de i18next (`src/i18n.ts`)

```ts
// src/i18n.ts
import i18n from "i18next";
import { initReactI18next } from "react-i18next";

i18n
  .use(initReactI18next)
  .init({
    fallbackLng: "fr",
    ns: [],                              // aucun namespace chargé à l'init — lazy-load uniquement
    interpolation: { escapeValue: false }
  });

export default i18n;
```

Points clés :
- **`fallbackLng: "fr"`** : si une clé est absente dans la langue active, i18next tente le français.
- **`ns: []`** : aucun namespace n'est déclaré à l'initialisation. Chaque module enregistre son propre namespace via `addResourceBundle` (voir ci-dessous).
- **`lng` absent** : la langue active n'est pas fixée à l'init. C'est `I18nBridge` qui synchronise i18next avec la locale du `LocalizationContext` au montage et à chaque changement.
- **`escapeValue: false`** : les valeurs interpolées ne sont pas échappées (React gère le XSS).

## Contexte de localisation

### Définition du contexte

```tsx
// src/contexts/LocalizationContext.tsx
import { Locale, LocalizedString } from '@/types/locale-schema';
import { createContext } from 'react';

interface LocalizationContextType {
  currentLocale: Locale;
  setLocale: (locale: Locale) => void;
  t: (text: LocalizedString, fallback?: string) => string;
  availableLocales: readonly Locale[];
}

export const LocalizationContext = createContext<LocalizationContextType | null>(null);
```

Le contexte est **nullable** (`createContext<... | null>(null)`) — les hooks qui le consomment vérifient sa présence et lèvent une erreur explicite s'il est absent.

### Provider

```tsx
// src/contexts/LocalizationProvider.tsx
import { type ReactNode, useState, useEffect } from 'react';
import { Locale, LOCALES, LocalizedString } from '@/types/locale-schema';
import { LocalizationContext } from './LocalizationContext';

interface LocalizationProviderProps {
  children: ReactNode;
  defaultLocale?: Locale;
  availableLocales?: readonly Locale[] | Locale[];
}

export function LocalizationProvider({
  children,
  defaultLocale = 'fr',
  availableLocales = LOCALES
}: LocalizationProviderProps) {
  const [currentLocale, setCurrentLocale] = useState<Locale>(defaultLocale);
  const [isClient, setIsClient] = useState(false);

  // Garde SSR : marque le passage côté client après hydratation
  useEffect(() => {
    setIsClient(true);
  }, []);

  // Lit localStorage uniquement côté client pour éviter les mismatches SSR
  useEffect(() => {
    if (!isClient) return;
    const savedLocale = localStorage.getItem('preferred-locale') as Locale;
    if (savedLocale && availableLocales.includes(savedLocale)) {
      setCurrentLocale(savedLocale);
    }
  }, [isClient, availableLocales]);

  const setLocale = (locale: Locale) => {
    setCurrentLocale(locale);
    if (typeof window !== 'undefined') {
      localStorage.setItem('preferred-locale', locale);
    }
  };

  const t = (text: LocalizedString, fallback = 'Missing translation'): string => {
    if (!text) return fallback;
    if (text[currentLocale]) return text[currentLocale];   // locale courante
    if (text[defaultLocale]) return text[defaultLocale];   // locale par défaut
    for (const locale of availableLocales) {               // n'importe quelle locale
      if (text[locale]) return text[locale];
    }
    return fallback;
  };

  return (
    <LocalizationContext.Provider value={{ currentLocale, setLocale, t, availableLocales }}>
      {children}
    </LocalizationContext.Provider>
  );
}
```

Points clés :
- **`defaultLocale`** et **`availableLocales`** : configurés en pratique depuis `config.meta.defaultLang` et `config.meta.languages` (voir [Montage dans `RootLayout`](#montage-dans-rootlayout)).
- **`isClient`** : garde SSR — `localStorage` n'est jamais accédé côté serveur.
- **`preferred-locale`** : clé localStorage pour persister la locale choisie entre les sessions.
- **`t`** : résolution en cascade — locale courante → locale par défaut → n'importe quelle locale → fallback string.
- **`setLocale`** : change la locale en mémoire et persiste dans `localStorage`.

### Hook `useLocalization`

```ts
// src/hooks/useLocalization.tsx
import { LocalizationContext } from "@/contexts/LocalizationContext";
import { useContext } from "react";

export function useLocalization() {
  const context = useContext(LocalizationContext);
  if (!context) {
    throw new Error('useLocalization must be used within a LocalizationProvider');
  }
  return context;
}
```

Expose `{ currentLocale, setLocale, t, availableLocales }`. Lève une erreur explicite si utilisé en dehors du `LocalizationProvider`. C'est via ce hook que `useT` accède à la fonction `t` de résolution des `LocalizedString`.

## Bridge i18n (`I18nBridge`)

```tsx
// src/contexts/I18nBridge.tsx
import i18n from "@/i18n";
import { I18nextProvider } from "react-i18next";
import { useEffect } from "react";
import { useLocalization } from "@/hooks/useLocalization";

/**
 * Met i18next au même locale que `LocalizationProvider`
 * et fournit le contexte react-i18next à toute l'arborescence.
 */
export function I18nBridge({ children }: { children: React.ReactNode }) {
  const { currentLocale } = useLocalization();

  useEffect(() => {
    if (i18n.language !== currentLocale) {
      i18n.changeLanguage(currentLocale);
    }
  }, [currentLocale]);

  return <I18nextProvider i18n={i18n}>{children}</I18nextProvider>;
}
```

Points clés :
- **`I18nextProvider`** : fournit l'instance i18next à `useTranslation()` dans toute l'arborescence enfant.
- **Synchronisation** : à chaque changement de `currentLocale` (ex. : l'utilisateur change de langue), `i18n.changeLanguage()` est appelé pour que `useTranslation()` reflète la même langue que `useLocalization()`.
- `I18nBridge` doit être monté **à l'intérieur** de `LocalizationProvider` (il consomme `useLocalization`).

## Montage dans `RootLayout`

Dans `src/RootLayout.tsx`, le sous-composant `SiteShell` monte la chaîne de contextes i18n :

```tsx
function SiteShell() {
  const { config } = useSite();

  return (
    <LocalizationProvider
      defaultLocale={config.meta.defaultLang}
      availableLocales={config.meta.languages}
    >
      <I18nBridge>
        {/* … reste de l'arborescence … */}
      </I18nBridge>
    </LocalizationProvider>
  );
}
```

- `defaultLocale` et `availableLocales` sont tirés du JSON de configuration (`config.meta.defaultLang`, `config.meta.languages`), pas de la constante `LOCALES`.
- `I18nBridge` est imbriqué **dans** `LocalizationProvider` afin de pouvoir lire `currentLocale` via `useLocalization`.

## Hook `useT`

`useT` est un **hook hybride** qui gère à la fois les clés i18next (namespace) et les objets `LocalizedString` (configuration JSON) :

```ts
// src/hooks/useT.ts
import { useTranslation } from "react-i18next";
import { useLocalization } from "@/hooks/useLocalization";
import { LocalizedString } from "@/types/locale-schema";

export function useT(namespace?: string) {
  const { t: tNs } = useTranslation(namespace);
  const { t: tData } = useLocalization();

  return (key: string | LocalizedString, fallback?: string, interpolationParams?: Record<string, unknown>) => {
    if (typeof key === "string") {
      const options = {
        defaultValue: fallback || key,
        ...(interpolationParams || {})
      };
      const k = tNs(key, options);
      return k === key && fallback ? fallback : k;
    }
    return tData(key, fallback);
  };
}
```

**Deux modes** :
- Si `key` est un `string` : utilise `react-i18next` avec le namespace fourni (traductions statiques enregistrées par `addResourceBundle`). Le `defaultValue` est `fallback || key`, de sorte que la clé s'affiche si la traduction est absente. Si i18next renvoie la clé telle quelle et qu'un `fallback` est fourni, le `fallback` est retourné.
- Si `key` est un `LocalizedString` : délègue à `useLocalization().t` avec résolution en cascade par locale. `interpolationParams` est ignoré dans ce mode.

**`namespace`** (optionnel) : identifie le namespace i18next (ex. `"modules/profil"`). Sans namespace, `useT()` fonctionne quand même pour les clés string (namespace par défaut de i18next) et pour les `LocalizedString`.

## Exemple d'utilisation

### Résolution d'un `LocalizedString` de la config JSON

```tsx
import { useT } from "@/hooks/useT";

export function HeroSection({ props }) {
  const t = useT();   // pas de namespace : uniquement LocalizedString
  return (
    <section>
      <h1>{t(props.headline)}</h1>
      {props.subhead && <p>{t(props.subhead)}</p>}
    </section>
  );
}
```

### Traduction de clés internes avec namespace

```tsx
import { useLoadNamespace } from "@/hooks/useLoadNamespace";
import { useT } from "@/hooks/useT";

export function LoginForm() {
  const { loaded } = useLoadNamespace("modules/auth");
  const t = useT("modules/auth");

  if (!loaded) return <div>Loading…</div>;

  return (
    <form>
      <label>{t("email_label")}</label>
      <input type="email" placeholder={t("email_placeholder")} />
      <button>{t("submit_button")}</button>
    </form>
  );
}
```

### Interpolation de paramètres

```tsx
const t = useT("modules/profil");
// t("greeting", undefined, { name: "Alice" }) → "Bonjour Alice"
```

## Namespaces par module

### Pattern d'enregistrement

Chaque module possède un fichier `i18n.ts` (ou `i18n/i18n.ts`) qui importe l'instance i18next globale et enregistre ses bundles de traduction **statiquement** via `addResourceBundle` :

```ts
// src/modules/auth/i18n.ts
import i18n from "@/i18n";
import fr from "./i18n/fr.json";
import en from "./i18n/en.json";

i18n.addResourceBundle("fr", "modules/auth", fr, true, true);
i18n.addResourceBundle("en", "modules/auth", en, true, true);
```

Signature : `addResourceBundle(language, namespace, resources, deep, overwrite)` — les deux derniers paramètres (`true, true`) activent la **fusion profonde** et l'**écrasement** des clés existantes, permettant aux modules de charger leurs bundles sans conflit même si le namespace a déjà été partiellement initialisé.

Ce fichier doit être importé (effet de bord) quelque part dans le module, par exemple en tête du composant principal :

```ts
import "@/modules/auth/i18n";
```

L'import déclenche l'enregistrement synchrone du bundle. Dès lors, `useT("modules/auth")` peut résoudre les clés sans attente.

### Organisation des fichiers i18n

Structure type (fr + en pour tous les modules) :

```
src/
  modules/
    auth/
      i18n.ts              ← enregistre "modules/auth"
      i18n/
        fr.json
        en.json
    profil/
      i18n.ts              ← enregistre "modules/profil"
      i18n/
        fr.json
        en.json
    coform/
      i18n/
        i18n.ts            ← enregistre "modules/coform" (chemin imbriqué)
        fr.json
        en.json
  components/
    layout/
      i18n.ts              ← enregistre "components/layout"
      i18n/
        fr.json
        en.json
```

## Chargement dynamique d'un namespace (`useLoadNamespace`)

### Implémentation

```ts
// src/hooks/useLoadNamespace.tsx
import { useTranslation } from "react-i18next";
import { useEffect } from "react";

const isServer = typeof window === "undefined";

export function useLoadNamespace(ns: string) {
  const { i18n } = useTranslation();
  const loaded = i18n.hasResourceBundle(i18n.language, ns);

  useEffect(() => {
    if (!loaded) {
      i18n.loadNamespaces(ns);
    }
  }, [loaded, i18n, ns]);

  // En SSR, on considère toujours comme chargé pour éviter le mismatch d'hydration
  // Les traductions manquantes afficheront la clé, ce qui est acceptable
  if (isServer) {
    return { loaded: true };
  }

  return { loaded: i18n.hasResourceBundle(i18n.language, ns) };
}
```

Points clés :
- Obtient l'instance `i18n` via `useTranslation()` (jamais par import direct — respecte le contexte fourni par `I18nBridge`).
- `i18n.hasResourceBundle(i18n.language, ns)` : vérifie si le bundle est déjà enregistré pour la langue active.
- **`useEffect`** : si le bundle est absent, appelle `i18n.loadNamespaces(ns)` de façon asynchrone. En pratique, les namespaces sont pré-enregistrés statiquement par `addResourceBundle` — ce chemin ne s'exécute que si le module a omis l'import de son `i18n.ts`.
- **Garde SSR** : retourne `{ loaded: true }` côté serveur pour éviter les mismatches d'hydratation. Les clés non résolues affichent la clé brute, ce qui est acceptable.
- **Ré-évaluation** : si `ns` change, l'effet se ré-exécute et charge le nouveau namespace si besoin.

### Utilisation avec garde de rendu

Utilisé lorsque le composant ne doit pas s'afficher avant que les traductions soient disponibles (formulaires, interfaces critiques) :

```tsx
import { useLoadNamespace } from "@/hooks/useLoadNamespace";
import { useT } from "@/hooks/useT";
import "@/modules/auth/i18n";   // déclenche addResourceBundle au chargement du chunk

export function LoginForm() {
  const { loaded } = useLoadNamespace("modules/auth");
  const t = useT("modules/auth");

  if (!loaded) {
    return <div className="flex items-center justify-center py-10 text-muted-foreground">Loading…</div>;
  }

  return (
    <form>
      <label>{t("email_label")}</label>
      <input type="email" placeholder={t("email_placeholder")} />
      <button>{t("submit_button")}</button>
    </form>
  );
}
```

### Utilisation sans garde de rendu

Lorsque les traductions sont pré-enregistrées et que les clés manquantes sont acceptables (elles affichent la clé brute), le `loaded` peut être ignoré :

```tsx
import { useLoadNamespace } from "@/hooks/useLoadNamespace";
import { useT } from "@/hooks/useT";

export function AmpliIntro(props: AmpliIntroProps) {
  useLoadNamespace("modules/ampli");   // retour non destructuré
  const t = useT("modules/ampli");
  // …
}
```
